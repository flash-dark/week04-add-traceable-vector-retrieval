## Context

第 3 课已经把材料正文按班级写入数据库，并用会话中的 `class_id` 做隔离。本变更在这之上增加可检索的切片。班级只从当前会话读取，请求里另带的班级编号无效。

问答不是让模型自由发挥。系统先用用户当前这一句做本班混合检索；只有拿到切片之后，才把材料标题、切片序号和正文交给生成过程。

## Decisions

### Decision 1: 正文与向量分开存放

切片正文放在 MySQL 表 `knowledge_chunks`。向量数据库只保存浮点向量和标识，不保存作为依据的正文。向量主键、`knowledge_chunks.id` 与 payload 中的 `chunk_id` 相同。检索时先得到向量主键，再回 MySQL 取 `chunk_text`。

### Decision 2: 三种检索模式

- 关键字检索只查本班切片的全文索引，匹配原文中出现的词，不调用嵌入。
- 向量检索先把问句嵌入，再与切片向量计算余弦相似度。低于 0.35 的切片丢弃。
- 混合检索两条路径各自排名，再用 RRF 融合：`1 / (60 + 关键字名次) + 1 / (60 + 向量名次)`。只命中一路的切片只累加那一路的分数。两路都没有留下切片时，不改用更弱的结果凑数。

问答固定使用混合检索，取前 4 条。单独的检索接口可以指定模式，默认仍是混合。

### Decision 3: 班级过滤发生在两条路径之前

关键字查询和向量查询都先限定会话中的 `class_id`。向量库 payload 带 `class_id`，查询时同时作为过滤条件。调用方在查询参数或 JSON 中提交的 `class_id`、`role` 不参与判定。

### Decision 4: 出处使用稳定字段

每条命中至少包含：材料标识、材料标题、`chunk_index`、`start_offset`、`end_offset`、切片正文。偏移相对该材料入库时的正文字符位置。页面上的 `[1]`、`[2]` 与返回列表的顺序一致。

### Decision 5: 无切片时不调用生成模型

混合检索没有候选时，接口返回「资料中未找到相关内容」，`citations` 为空数组，并且不访问对话网关。有切片时，生成过程只能使用这最多 4 条切片的标题、序号和正文，不能再自行查询数据库或向量库。

### Decision 6: 切分策略

未指定策略时使用自动窗口：最大约 800 字，相邻切片重叠约 80 字，优先在空行、换行或句号处断开。也可按自定义分隔符，或按 Markdown 标题分章后再对过长章节使用自动窗口。同一次上传使用的策略必须写入该材料，重建索引时沿用或按新策略整份替换，不能留下旧切片和新切片混在一起。

## Risks

- 向量库写入失败而 MySQL 已提交时，编号会对不齐。写入必须在失败时回滚切片行，或能按材料重新嵌入并覆盖同一批主键。
- 只在应用层过滤班级、而向量查询本身不过滤时，其他班的近邻向量可能进入候选。因此向量查询的过滤条件与 SQL 的 `class_id` 条件都要存在。
- 把角色或班级放进客户端可改的参数，会覆盖会话。检索接口不读取这些字段。
